正式作业从 `assets/assembled/qwen3-tts-frozen-conditioning/` 加载本地已组装权重，没有接续历史实验或预检 checkpoint。以下依据该目录的 `assembly_report.json`、实际 safetensors 张量形状，以及正式提交快照 `7a4c303` 的加载 / 冻结 / optimizer 代码核对。当前模型是文本 LM 主干迁移到 TTS，音频预测模块从随机初始化开始训练。

主模型共 **914,643,008** 参数，其中可训练 **588,329,216**，冻结 **326,313,792**。可训练部分进一步分为文本 LM 迁移的 **440,467,456** 参数和新音频模块 **147,861,760** 参数。这里的“全量训练”表示训练全部允许更新的参数，没有使用 LoRA；并不表示文本前端和 speaker encoder 也解冻。

`from scratch` 指音频模块最初没有复制已有模型权重：在本地组装时，以 seed 42 完成初始化并保存 FP32 权重，正式启动直接加载它们，不在每次启动时重新组装。Linear / embedding 按模型初始化规则生成，norm 等使用各自默认初值。当前训练已有更新，因此正在运行的音频模块已不再是初始随机权重；resume 会加载 checkpoint 中的训练后参数及完整训练状态。

需要区分两类 embedding：文本 embedding 和 text projection 均来自官方 TTS 且冻结；codec embedding 是新初始化并训练的，包括位于 codec 词表中的 BOS / EOS / PAD 等控制 token 对应参数。首码本 embedding 和 codec head 也不共享权重。官方 TTS 的 Talker Transformer、codec embedding / head 和 Code Predictor 权重均未加载，文本 LM 的原始文本输出 head 也未加载。主干并非从零开始，使用的是纯文本 `Qwen3-0.6B-Base` 的 Transformer 权重。

训练模型中的 codec embedding 是 token 查表，不是音频 tokenizer 内部的量化码本。后者属于固定的预训练 codec；前者由本次训练学习。16 组 token 的 embedding 相加构成输入 Talker 的音频帧向量；residual embedding 同时用于 Code Predictor 的 teacher forcing，因此这些 embedding 都参与反向传播。Code Predictor 合计 141,570,304 参数；它的跨模块 projector 是无参数 Identity，不存在被遗漏的随机 Linear。

该 Identity 行为与官方 0.6B 一致：[官方实现](https://github.com/QwenLM/Qwen3-TTS/blob/main/qwen_tts/core/models/modeling_qwen3_tts.py) 仅在 Talker / Code Predictor 的 hidden size 不同时创建 Linear，否则使用 Identity；[官方 0.6B 配置](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-0.6B-Base/blob/main/config.json) 两侧均为 1,024。这里说明连接结构一致，不代表本次权重初始化和训练方案与官方相同。

当前 merged features 直接提供固定 speaker embedding 和 codec IDs。训练不在线执行 speaker encoder 或音频编码器，也不会更新这些预计算特征。Speaker encoder 保留在模型中以支持推理；codec decoder 在生成评测时将预测 IDs 转为波形，不参与本次反向传播。文本 embedding 冻结也不等于模型不能学习利用文本：可训练 Talker 的 attention / MLP 会持续学习文本、speaker 条件和音频之间的关系。

表中 LR 是 WSD 的峰值，而非每一步都使用的常数；两组都按同一数据消费进度 warmup / steady / decay。冻结参数不进入 optimizer，不受 weight decay 更新。BF16 是计算精度选择，与冻结范围无关。

Talker 与 Code Predictor 联合训练：同一次前向计算首码本 CE 和剩余 15 个码本的 CE，按 `first_ce + 0.3 * residual_ce` 合并反向传播，再由同一个 optimizer 更新。Code Predictor 输入中的 Talker hidden states 没有 detach，因此 residual loss 也反传到 Talker。它是一个 5 层 Transformer，在码本维度上使用真实前序 token 做 teacher forcing，预测后续 15 个码本，并非 15 个独立训练的 Transformer 层。

这与[官方公开微调脚本](https://github.com/QwenLM/Qwen3-TTS/blob/main/finetuning/sft_12hz.py)的联合更新、0.3 residual 权重一致。[技术报告 §3.1–3.2](https://arxiv.org/html/2601.15621v1#S3)介绍了分层预测与整体预训练阶段，但没有明确披露 MTP 是否曾单独预训练或分阶段解冻；不能据微调脚本声称已复现官方全部预训练流程。

来源记录中的 `assets/training/sources/` 是组装当时的历史路径；这些基础模型后来已整理到 `assets/base/`。正式训练读取 assembled 产物，不依赖该旧路径，也未因目录移动重新初始化。

## 文本与音频输入怎样融合

当前使用 `qwen3_non_streaming` 输入协议，实现见 `qwen3_train/models/protocol.py`。数据 build 用 assembled 模型配套的文本 tokenizer 将 merged 表的 text 转为整数 IDs（`add_special_tokens=False`）并缓存；reader 再添加 TTS text BOS / EOS。Tokenizer 是固定的分词规则与词表，不是参与反向传播的神经网络。文本 IDs 查 151,936 × 2,048 的 text embedding，再经过 `2048 → 2048 → 1024` 的 SiLU MLP 得到逐 token 文本向量，查表和 MLP 都冻结。

音频每帧有 16 个整数 ID。第 0 组查 Talker 的 codec embedding；第 1–15 组分别查 Code Predictor 的 15 张 embedding 表，每次得到 1,024 维向量。同一帧的 16 个向量逐元素相加，形成一个 1,024 维帧向量，不把 16 组展开成 Talker 的 16 个时间位置，也不拼成 16,384 维。这里的 16 张查表都是新初始化、可训练的参数；codec IDs 固定并不意味着其 embedding 冻结。相同整数 ID 在不同码本中查不同表，不能与文本 token ID 混用。

统一到 1,024 维后，每个位置按双通道相加：

```text
文本位置 = text_projector(text_embedding[text_id]) + codec_embedding[codec_pad]
音频位置 = sum(codec_embedding_g[code_g], g=0..15) + projected_text_pad
说话人位置 = cached_speaker_embedding + projected_text_pad
音频 BOS = codec_embedding[codec_bos] + projected_text_pad
projected_text_pad = text_projector(text_embedding[tts_pad])
```

`projected_text_pad` 来自冻结文本前端；`codec_pad` 属于可训练音频 embedding，所以文本位置上的最终输入向量仍含一个可训练的公共偏置项。这里的 PAD 是另一模态的协议占位向量，不是为了补齐 batch 长度而加入的无效位置，与 FA2 无长度 padding 的组批不冲突。

每条样本沿序列维度拼接为：角色前缀 → 音频控制前缀 → speaker 条件 → 完整文本（含 text BOS/EOS）→ codec BOS → 逐帧音频向量。文本 token 数和音频帧数无需相等，不做逐字与逐帧强制对齐；因果 self-attention 让音频位置读取前面的完整文本、speaker 条件和历史音频。训练用真实历史 codec 做 teacher forcing，codec BOS 位置预测第一帧、上一帧位置预测下一帧、最后一帧位置预测 EOS；目标帧不会提前暴露给预测该帧的位置。打包多条样本时各自有独立 FA2 序列边界和重置的位置编号，不跨样本 attention。

Code Predictor 另将一帧对应的 Talker hidden state 与该帧真实的前序码本 embedding 沿短序列拼接，使用因果 attention 预测剩余码本；这与 Talker 中“同帧 16 组 embedding 相加”的用途不同，但复用同一组音频 embedding 参数。

## Attention 选择与大 batch 验证

Talker 使用 FlashAttention-2 的 varlen packing，每条样本有独立边界，无长度 padding。Code Predictor 每个 frame 是一条固定 16 位置的短序列，使用原生 memory-efficient SDPA / math，不需要 padding。

选择依据：

- [Qwen 官方微调脚本](https://github.com/QwenLM/Qwen3-TTS/blob/main/finetuning/sft_12hz.py) 使用 BF16 + FA2，默认 batch size 为 2 条音频；这不等于验证了每卡数万 frames 的训练规模。
- [vLLM-Omni Code Predictor](https://github.com/vllm-project/vllm-omni/blob/main/vllm_omni/model_executor/models/common/qwen3_code_predictor.py) 使用原生 SDPA，并保留与 Hugging Face 一致的数值计算。它是推理实现，可参考后端选择，但不能代替训练反向传播测试。
- 本环境为 PyTorch 2.8 / CUDA 12.6、flash-attn 2.8.3.post1。独立测试中，固定长度 16、head dimension 128 的 FA2 在 batch 3,000 正常，16,000 出现非法内存访问；完整模型的大 batch 出现 NaN 梯度。原生 SDPA 的 Flash 后端也复现了问题，memory-efficient / math 后端的同形状测试通过。因此训练显式关闭原生 Flash / cuDNN SDPA 后端，外部 Talker FA2 不受影响。
- 不引入自研 attention kernel，不改变预测目标、码本位置或 token loss 归一化。

本地四卡完整模型在每卡 30,000 frames / 48,000 tokens 下完成 16 步、两次验证和 checkpoint。稳态吞吐约 1,340–1,390 音频秒/秒，GPU 实际占用约 65 GiB，计算时利用率 100%；多数稳态步的数据等待不足 0.01 秒。首次 worker 启动和 epoch 切换有额外预取延迟。正式预算以随后 32 卡、较大代表性数据集的实测为准，目标是约 80–85% 实际显存占用并保留峰值余量。

## 数据等待与严格恢复

训练记录所有 rank 的最大 / 平均取 batch 等待、等待占整步比例、batch 准备耗时、最大 PyTorch 峰值显存，以及全局音频吞吐。NVML 每 10 秒记录每张 GPU 的利用率、实际显存和功耗。取 batch 等待只计算主训练线程被数据加载阻塞的时间，已经与计算重叠的预取不计入等待。

DataLoader 使用独立随机生成器、persistent workers、pin memory 和可配置预取。验证也支持预取，极小验证集直接读取以避免 worker 启动成本。单条坏数据隔离跳过；任何 rank 的 microbatch 全坏时，所有 rank 同步跳过，记录坏样本和连带丢弃数量。

Checkpoint 只提交已完成更新的数据进度，包含 epoch、next_batch、全局消费样本数，以及 optimizer / scheduler / 各 rank RNG。恢复按固定 seed、epoch 和预算重建 batch，重读尚未消费的预取数据。worker 数和预取深度可以改变；world size、模型、数据、batch 预算和 LR 计划必须一致，否则拒绝恢复。

真实双卡回归入口 `tests/check_epoch_resume.py` 验证坏 codec、固定 holdout、3 epoch WSD、首步验证保存，以及恢复时改变 workers / prefetch。逐步比较 LR、loss、梯度范数和样本数，并对最终模型权重要求逐位一致。BF16 和 FP32 的上述双卡回归均通过，62 项 pytest 回归、Ruff 检查和格式检查通过。
