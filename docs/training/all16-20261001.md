# 2026-10-01：16 数据集 BF16 全量训练

## 数据与训练计划

实验配置为 `configs/supervised-tts-20260929-all16-bf16-32gpu-lr3e-4-bblr1e-4-ep3-wsd.yaml`，run 使用同名目录，位于 `/workspace/LM-TTS-Training-Runs/`。作业 ID、提交时间、有效配置和代码快照保存在 `submissions/`。

Selection 为 `tts-selection-supervised-tts-20260929T151539bjt-01`，绑定 2026-10-01 发布的 16 个 merged features 表。全量 build 验证通过：128,220,178 条样本，其中训练 128,091,959 条、验证 128,219 条。按数据集固定抽取约 0.1%，seed 42，行索引不重叠；不保证说话人 / 文本隔离。源数据总音频约 357,506.83 小时，最大单条 1,377 codec frames。训练 / 验证各数据集共抽查 252 条真实 payload，全部成功读取。

索引位置为 `data/builds/supervised-tts-20260929-merged-20261001-all16/`。它包含固定版本引用、text token、长度索引和划分，不复制 codec / speaker 大字段，源文件必须保留。

使用 4 节点 × 8 张 A800、FSDP2、BF16、token loss，residual 权重 0.3，训练 3 个 epoch。新增模块 / backbone 峰值 LR 为 `3e-4 / 1e-4`，不随卡数线性放大。WSD 根据已消费样本占总 3 epoch 的比例调度：前 0.03 epoch 线性 warmup，steady 到 2.7 epoch，最后 0.3 epoch 余弦衰减至峰值的 10%。因此无需预先猜测 dynamic batching 的总步数。

先在第 100 步执行完整验证和保存，之后每 2500 步同时执行，保留最近两份 checkpoint。计划观察到第 2500 步的验证和保存完成，并确认训练继续。验证 loss 使用全部训练 GPU；WER / CER、DNSMOS 和 WavLM 是独立生成音频评分流程。

## Attention 选择与大 batch 验证

Talker 使用 FlashAttention-2 的 varlen packing，每条样本有独立边界，无长度 padding。Code Predictor 每个 frame 是一条固定 16 位置的短序列，使用原生 memory-efficient SDPA / math，不需要 padding。

选择依据：

- [Qwen 官方微调脚本](https://github.com/QwenLM/Qwen3-TTS/blob/main/finetuning/sft_12hz.py) 使用 BF16 + FA2，默认 batch size 为 2 条音频；这不等于验证了每卡数万 frames 的训练规模。
- [vLLM-Omni Code Predictor](https://github.com/vllm-project/vllm-omni/blob/main/vllm_omni/model_executor/models/common/qwen3_code_predictor.py) 使用原生 SDPA，并保留与 Hugging Face 一致的数值计算。它是推理实现，可参考后端选择，但不能代替训练反向传播测试。
- 本环境为 PyTorch 2.8 / CUDA 12.6、flash-attn 2.8.3.post1。独立测试中，固定长度 16、head dimension 128 的 FA2 在 batch 3,000 正常，16,000 出现非法内存访问；完整模型的大 batch 出现 NaN 梯度。原生 SDPA 的 Flash 后端也复现了问题，memory-efficient / math 后端的同形状测试通过。因此训练显式关闭原生 Flash / cuDNN SDPA 后端，外部 Talker FA2 不受影响。
- 不引入自研 attention kernel，不改变预测目标、码本位置或 token loss 归一化。

本地四卡完整模型在每卡 30,000 frames / 48,000 tokens 下完成 16 步、两次验证和 checkpoint。稳态吞吐约 1,340–1,390 音频秒/秒，GPU 实际占用约 65 GiB，计算时利用率 100%；多数稳态步的数据等待不足 0.01 秒。首次 worker 启动和 epoch 切换有额外预取延迟。正式预算以随后 32 卡、较大代表性数据集的实测为准，目标是约 80–85% 实际显存占用并保留峰值余量。

## 32 卡预算预检

作业 `pt-02adzadg` 使用更大的约 65k 条代表性数据，完成 24 步及第 4 / 12 / 24 步验证和 checkpoint。每卡预算确定为 **32,000 frames / 50,000 tokens**，梯度累积 1。

舍去前三步后，包含代表性小数据集的 epoch 切换，按总音频秒 / 总训练耗时计算吞吐约 **10,283 音频秒/秒**；训练步中位数 **7.38 秒**。32 张卡的 NVML 显存峰值为 **66.32–66.75 GiB**，约占可用显存的 **84%**；全局最大 PyTorch 分配峰值为 **60.77 GiB**。取 batch 等待中位数 **0.15 毫秒**，最大 **2.40 秒**，后者出现在重新填充数据队列时。完整统计在正式 run 的 `logs/verification/acp32-bf16-profile.json`。

按该吞吐粗算，3 epoch 的纯训练计算约 4.3 天；正式语料分布、存储读取、验证和保存都会影响总时长。到第 2500 步预计约 5 小时，使用正式运行日志持续修正。

## 数据等待与严格恢复

训练记录所有 rank 的最大 / 平均取 batch 等待、等待占整步比例、batch 准备耗时、最大 PyTorch 峰值显存，以及全局音频吞吐。NVML 每 10 秒记录每张 GPU 的利用率、实际显存和功耗。取 batch 等待只计算主训练线程被数据加载阻塞的时间，已经与计算重叠的预取不计入等待。

DataLoader 使用独立随机生成器、persistent workers、pin memory 和可配置预取。验证也支持预取，极小验证集直接读取以避免 worker 启动成本。单条坏数据隔离跳过；任何 rank 的 microbatch 全坏时，所有 rank 同步跳过，记录坏样本和连带丢弃数量。

Checkpoint 只提交已完成更新的数据进度，包含 epoch、next_batch、全局消费样本数，以及 optimizer / scheduler / 各 rank RNG。恢复按固定 seed、epoch 和预算重建 batch，重读尚未消费的预取数据。worker 数和预取深度可以改变；world size、模型、数据、batch 预算和 LR 计划必须一致，否则拒绝恢复。

真实双卡回归入口 `tests/check_epoch_resume.py` 验证坏 codec、固定 holdout、3 epoch WSD、首步验证保存，以及恢复时改变 workers / prefetch。逐步比较 LR、loss、梯度范数和样本数，并对最终模型权重要求逐位一致。BF16 和 FP32 的上述双卡回归均通过，62 项 pytest 回归、Ruff 检查和格式检查通过。

完整模型另做了 32 卡恢复对照：`pt-r7400sb8` 从 `pt-02adzadg` 的第 12 步恢复，workers 从 4 改为 2、prefetch factor 从 2 改为 4。第 13–24 步的 LR、loss、梯度范数、样本数和 token 数完全一致；第 24 步 checkpoint 元数据完全一致，完整权重 SHA256 均为 `faad7dd798b22647655273d18060cc254b9327a3a8c698fcef47462974ca78da`。报告归档在正式 run 的 `logs/verification/acp32-bf16-resume.json`。

正式训练确认稳定后删除预检 build 和临时 run，只保留全量 build、正式 run 及日志下的精简验证摘要。仓库内 `runs/` 的历史实验按既有保留规则保存。
